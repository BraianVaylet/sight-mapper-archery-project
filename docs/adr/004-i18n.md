# ADR-004 — ES y EN desde el dia uno; la API devuelve claves

- **Estado:** Aceptada
- **Fecha:** 2026-10-29
- **Relacionadas:** TECNICO §9, [errors.md](../errors.md)

## Contexto

Todos los competidores son solo ingles: es una ventaja para el mercado hispanohablante y una
condicion para el mercado global. Agregar i18n despues obliga a tocar cada pantalla. El MVP incluye
EN (decision 2026-10-29).

## Decision

1. Catalogos `es` y `en` en `@sight-mapper/i18n`, con **claves tipadas** (una clave inexistente es
   error de compilacion) y test de paridad entre idiomas.
2. **La API no manda prosa.** Errores con `messageKey` + `params`; el cliente traduce. Los emails
   (verificacion, recupero) se renderizan en el servidor con plantillas por idioma.
3. Numeros, fechas y unidades con `Intl` segun el locale (`es`: coma decimal).
4. Idioma inicial: el del navegador; luego, `profile.locale`.
5. Portugues preparado (agregar un catalogo) pero no abierto: se decide con datos.

## Alternativas consideradas

| Alternativa                    | Por que no                                               |
| ------------------------------ | -------------------------------------------------------- |
| Solo ES en el MVP              | Cierra el mercado principal (EE.UU.) y obliga a retrofit |
| La API traduce los mensajes    | Acopla idioma al servidor; cache y tests mas fragiles    |

## Consecuencias

- Positivas: diferenciador; ningun retrofit.
- Negativas: cada string nuevo cuesta dos traducciones; el DoD lo exige.

## Como se hace cumplir

ESLint (`i18next/no-literal-string`) en JSX. Test de paridad de claves. Test que verifica que todo
codigo de error tiene su `messageKey` en ambos catalogos. Revision de que ninguna respuesta HTTP
contiene prosa en la suite de integracion.
